# 飞书群级默认 Agent Profile 与会话模式

[English](2026-09-16-feishu-group-session-defaults-design.md) | [简体中文](2026-09-16-feishu-group-session-defaults-design.zh-CN.md)

状态：实现规格。2026-09-16 用户确认实现；群设置覆盖完整执行参数，验证结果单独记录。

## 1. 推荐方案

为“当前 Bot 在当前群”增加独立设置：**默认专家、Runtime、模型、思考强度、处理方式和工作区参数**。
负责人设置一次，后续符合触发规则的新会话自动使用该配置。

配置作用域为 `(bridge_id, chat_id)`。同一个 Bot 在不同群可以使用不同专家和处理方式；
同一个群中的多个 Bot 各自配置。群内连续会话也以这个作用域复用。

| 群内处理方式 | 会话如何创建和复用 | 执行环境 |
| --- | --- | --- |
| 本群继续同一对话 | 本群新的对话入口进入同一个连续会话，直至负责人新开会话 | 普通执行环境；沿用共享会话的执行身份规则 |
| 每个话题独立 | 新话题创建一个 Session，同一话题继续该 Session | 普通执行环境，仍保留执行鉴权 |
| 每个话题独立（用户隔离） | 新话题创建一个 Session，同一话题继续该 Session | 必须以可识别用户身份启动，执行环境满足隔离要求 |

“用户隔离”沿用现有执行身份与运行环境语义，不增加“同一话题按发送者拆成多个 Session”规则。
同一话题后续输入仍经过现有 execution authorization，不能因群协作开放而绕过执行权限。
Linux 隔离全局开关提供执行能力，不自动覆盖飞书会话的模式选择。新建普通话题和连续
会话明确使用 passthrough；新建用户隔离话题固定为 linux-dac，不可用时拒绝启动。
未配置群和私聊使用 Bot 默认模式，其他群使用各自快照。已有会话保留启动时的环境，
不因保存群设置迁移。普通模式仍保留已识别身份与 actor credential，不绕过执行鉴权。

群协作的 `owner_only|shared` 决定谁可发起任务；Bot governance 和 execution authorization
继续各自生效。它们与“默认专家”“处理方式”分别展示和校验。

### 方案比较

| 方案 | 收益 | 代价与结论 |
| --- | --- | --- |
| 群级专家与处理方式一起设置 | 一个 Bot 可以在不同群承担不同工作；使用入口一致 | 需要增加群级连续会话绑定；推荐 |
| 只恢复群默认专家，模式仍由 Bot 统一决定 | 实现量较小 | 无法让两个群分别使用单会话和话题模式，不能完整满足需求 |
| 每个群配置独立 Bot Profile | 可复用现有 Bot 级设置 | 增加应用、凭据和运维成本，不作为常规使用方法 |

## 2. 使用方法

### 实验功能开关

群独立配置由实例级 `bridge.feishu.group_settings.enabled` 控制，默认 `false`。
负责人在私聊 `/amux` → 实验功能开启“群独立配置”，通过“保存并重启”生效。
保存配置不热更新正在运行的 Hub；实验页同时展示已保存但待重启的状态。
关闭时隐藏群配置编辑入口，旧卡片、自然语言、命令及本机 CLI 不得绕过开关。
未配置群和私聊保留既有 Bot 行为；已经保存独立策略的群暂停新输入和自动任务，
不回退全局连续会话、不降低隔离要求。配置、会话关联和在途输出保留，重新开启
并重启后恢复已保存策略。旧实验卡未提交新字段时保留已保存值，所有实验设置原子保存。

### 主入口：群里发起，负责人私聊配置

1. 负责人在目标群中新发一条群消息 `@机器人 /amux`，作为管理入口。
2. 群内显示当前群的配置摘要；负责人收到带群名称和群标识的“当前群设置”私聊卡片。
3. 卡片提供专家、Runtime、模型、思考强度、处理方式和过程展示，以及工作区参数和“保存本群设置”。
4. 保存成功后显示生效范围和新会话的默认专家。普通成员在群中 `@机器人 + 任务` 即可使用。

沿用现有群管理进入私聊的方式，不在群中展示系统维护操作。普通成员只可查看摘要。
设置权限沿用 Bot owner，不把飞书群管理员自动视为 amux 管理者。

示例卡片（专家引用仅为示意，必须来自已安装的 Pack）：

```text
当前群设置 · 代码评审群
当前助手：开发助手

默认专家       Reviewer · team/reviewer
处理方式       每个话题独立（用户隔离）
使用权限       群成员可发起任务

[选择专家]  [选择处理方式]  [保存本群设置]

新话题使用以上设置；已有话题保留原来的会话和专家。
```

专家选择器复用现有可搜索的 Profile 目录，并提供“跟随助手默认专家”。
选择继承时，同时显示当前解析出的专家和来源，不能只显示“默认”。
处理方式从三种模式中明确选择；首次打开时以当前助手设置预填，保存后成为本群自己的选择。
后续修改 Bot 级处理方式不会改变已配置群的处理方式。

连续会话卡片额外区分：

```text
当前会话专家：team/reviewer
新会话默认专家：team/coder
[新开连续会话]
```

“新开连续会话”明确说明将从空白上下文开始。普通“保存默认专家”不隐式替换当前会话。

### 命令入口

以下为新增或恢复的 Bridge 管理命令，必须由负责人在群管理入口执行：

```text
@机器人 /workspace default-agent team/reviewer
@机器人 /workspace default-agent inherit
@机器人 /workspace interaction singleton
@机器人 /workspace interaction thread
@机器人 /workspace interaction thread_isolated
@机器人 /workspace status
```

恢复现有“这个群默认用 <profile>”解析入口，使其等价于 `default-agent` 设置。
保留 `/workspace mode owner_only|shared` 的访问权限语义，另用 `interaction` 设置处理方式。
`default-agent inherit` 只清除专家覆盖，仍保留本群处理方式和本群会话范围。

第一次通过命令修改任一字段时，原子保存完整群策略：未指定的处理方式取当时 Bot 的有效值，
未指定的专家取当时 Bot 的有效值。模式切换命令直接应用并回复影响说明；卡片保存提供确认说明。
管理命令及卡片操作必须在进入 Agent 前由 Bridge 处理，不能作为普通 Prompt 去修改配置。

## 3. 生效与继承规则

### 新会话选择专家

普通新会话按以下优先级选择，选中后再进行 Profile、模型、Runtime 和权限校验：

```text
本次明确指定的 Profile（例如已有 /run <profile> -n <name>）
  > 本群明确设置的 Profile
  > Bot 默认 Profile
  > 发行版默认 Profile
```

这里的最后一级沿用发行版注册的默认值，不在公共实现中写死内部专家名称。
明确指定但不可用的 Profile 必须报错，不得继续向低优先级回退。
新会话冻结解析后的 Profile 与执行参数；Pack 更新也沿用现有快照规则。

已有话题、连续会话的后续输入、sleep 后唤醒以及重启恢复，均继续使用原会话快照。
`/bind` 采用被绑定 Session 自身的专家；显式 `/run` 不改变群默认。
隔离话题的 `/run` 和 `/bind` 仍需满足有效隔离要求，显式 Profile 不能覆盖该要求。

群设置复用助手编辑器的 Runtime、模型、思考强度和过程展示能力，并完整保存本群的
目标机器、工作目录、附加参数、空闲回收时间、上下文条数和会话限额。首次编辑时预填当前
有效值；保存后这些参数独立于 Bot 默认，不会被后续助手设置修改覆盖。专家可单独选择继承。
空 Runtime 表示使用 Profile 原生运行引擎；空模型、空思考强度表示所选引擎默认值。
模型允许输入引擎支持的原生名称，必须保留现有 Runtime/模型策略与思考强度校验。

保存以完整配置为事务单位，同时校验 workspace 权限模式和执行参数。无效参数不得部分写入。
创建时再次检查目标 Runtime、执行身份、凭据和隔离能力；明确失败不能静默回退。
Profile 切换不自动清空不兼容的参数，卡片指出需调整的字段。

### 修改设置后的行为

| 操作 | 已有会话 | 后续行为 |
| --- | --- | --- |
| 修改群默认专家 | 原 Profile 和上下文不变 | 新话题、新开的连续会话采用新默认 |
| 修改 Bot 默认专家 | 原会话不变；群显式覆盖不变 | 选择“跟随助手默认专家”的群在新建时使用新值 |
| 普通话题与用户隔离话题互换 | 原话题保留原执行身份和环境 | 新话题采用新隔离要求；卡片说明已有话题保留原执行环境 |
| 话题模式改为本群连续会话 | 已绑定话题仍在原 Session 内继续 | 未绑定的新入口进入本群连续会话；不合并旧话题历史 |
| 本群连续会话改为话题模式 | 旧连续会话停止接受新输入，已接受的任务正常完成 | 新话题新建 Session；回复旧连续会话入口时提示另开话题 |
| 新开连续会话 | 原会话历史保留，已接受的任务正常完成 | 新入口使用新默认 Profile 和空白上下文 |

普通话题间切换隔离要求仅作用于新会话，不能把“开了用户隔离”呈现为旧会话已完成迁移。
卡片保存说明切换影响，新开连续会话需要确认；执行中的输出继续回所属群，不强制终止任务。
以后再次切回连续会话也创建新的空白会话，不自动复活旧连续会话。

群连续会话首次接受有效任务时延迟创建。创建失败不落 active 绑定，下一次可以重试。
当前 Session 意外消失时提示负责人恢复或新开，不把上下文丢失伪装成正常续聊。

## 4. 路由与上下文

配置读取形成一次一致的群启动策略快照，包含设置版本、专家来源、处理方式、
隔离要求及现有有效执行参数。新建链路使用同一快照，不在选专家后重新读取另一版隔离设置。

群内路由顺序：

1. 识别并鉴权 Bridge 管理操作，不触发 Agent。
2. 检查当前 Bot、当前群和输入者权限。
3. 已有话题绑定按原 Session 路由，继续执行其权限与生命周期规则。
4. 检查连续会话入口记录：属于已停用会话的旧回复入口只给出转场提示。
5. 对未绑定入口解析本群策略：话题模式走既有 topic router，连续模式走群级 Session。
6. 新建 Session 时完成 Profile projection、执行授权、隔离校验和持久化，再提交输入。

群连续会话的创建和设置锁包含 `bridge_id + chat_id`；去重保留真实来源群与话题，
输入合并与 stream 使用该群唯一的真实输入锚点绑定，输出直接发往所属群。不能继续只使用 `singleton:<bridge_id>`。同群并发首次输入只能创建一个当前连续会话。
设置保存与新建绑定使用版本校验，防止新建过程把旧策略写成新策略下的 active 绑定。

群连续会话可以跨本群话题复用 provider 历史，但不自动读取其他群或私聊历史。
每次输入保留发言者和来源话题；连续会话的输出、材料和权限卡直接发往所属群；独立的完成通知实验仍按其私聊提醒规则发送。
输出消息记录到同一会话的入口关联，回复这些消息可继续该会话。首次输入仅作为内部锚点，
不产生跳转到首次话题的提示。回复位置不随最后一条消息漂移，禁止使用 Bot 全局“最后回复位置”决定出口。
群单会话保证会话上下文分开，不宣称不同群具备独立 OS 用户、凭据或文件系统安全边界。
共享会话继续采用现有 `shared=true` 执行身份解析和 service principal 授权。

话题模式保持 topic-root 首轮注入及 shared thread context 的现有边界。
群连续会话复用 Session 队列和群消息输出机制，不因本功能额外开启 shared thread history。
执行环境的“用户隔离”不改变飞书群消息可见性，也不等价于禁止引用同话题可见消息。

### 群值守与其他入口

- 群值守的处理方式按目标群判断，只支持两种话题模式。不能因另一群或 Bot 默认采用
  singleton，就关闭此群的值守。
- 选择连续会话前，先通过已有入口关闭本群值守。保存时若本群仍在值守，提示冲突并拒绝保存，
  不做跨配置存储的隐式联动。其他群的值守配置不受这次保存影响。
- 值守未指定专用专家时，使用本群默认专家；已有明确值守执行覆盖仍优先，摘要显示
  “值守使用独立专家：X”。覆盖只改变执行参数，不能绕过群隔离要求。
- 自动来源不能解析出合法隔离执行身份时拒绝启动并记录原因，不冒用负责人身份。
- 文档评论、私聊和其他无群作用域的入口继续采用各自原有默认规则。

## 5. 实现边界

本能力属于公共核心，修改放在公共 `internal/bridge` 及对应模型中。
内部发行版继续通过既有 Profile 注册与 Pack 提供专家，不另建群设置实现。

使用 workspace 的一对一扩展表 `feishu_group_settings`：

| 字段 | 含义 |
| --- | --- |
| `bridge_id, chat_id` | 联合主键；记录存在表示该群启用独立设置 |
| `default_agent` | 可空；空值表示新建时继承 Bot 默认专家 |
| `interaction_mode` | `singleton` 或 `thread`，保存后为群自己的选择 |
| `isolation_required` | 仅 `thread` 可为 true；UI 的 `thread_isolated` 映射到此组合 |
| 完整执行与工作区参数 | Runtime、模型、思考强度、过程展示、目标、目录、参数、回收、上下文和配额 |
| `state_version` | 乐观并发控制；过期卡片保存时要求刷新 |
| `updated_by, updated_at` | 最近操作者与更新时间 |

原 `FeishuWorkspace.Mode` 继续承载 `owner_only|shared`。旧 `default_agent` 列不作为新的
显式覆盖来源，避免把历史预填值误判为用户选择。新增表为群 Profile 设置的唯一事实来源。

群设置保存当前连续会话的根消息指针，Session、创建时的 Profile 和目标继续由真实话题绑定保存，
Session/Launch/Turn 身份复用已有 Turn 收据。每个群最多一个当前默认连续会话；旧会话可以完成已接受任务。
另记录使用过该代次的输入根消息，用于模式切换后识别旧入口；这只是入口归属记录，
保留首次真实输入作为 Session 的内部绑定锚点，其他输入和输出消息记录到该绑定的关联；
群连续会话所有输出直接发送到所属群，普通话题输出仍留在对应话题。
输出定位复用并补齐现有 Turn 关联收据，重启后仍可恢复准确出口。

职责保持可分：群策略存储负责原子保存，策略解析负责继承与来源，路由负责选择绑定，
现有 session starter 负责创建，stream 负责按固定目的地呈现。查询卡片不创建策略或 Session。
Profile 目录更新/卸载的引用检查须同时覆盖群显式默认，不能漏掉仅被某群使用的 Pack。

## 6. 兼容与迁移

采用逐群启用，迁移数据库本身不改变现有路由。没有群策略记录的群继续执行旧 Bot 设置；
状态页说明未保存时沿用助手设置；旧 singleton 的 Bot 范围保持不变。
负责人第一次保存“本群设置”后，该群进入新的群作用域；保存确认说明将与旧全局连续会话分开。

启用时不复制或接管 Bot 全局 singleton 的历史、凭据和绑定。原先已接受的任务沿原收据完成，
后续本群入口受群策略约束。保留旧 BotSession 用于私聊及尚未启用的群。
已存在的话题 Session 保留绑定，不因启用群设置被停止。

已经启用的群不提供隐式退回 Bot 全局 singleton 的快捷操作。“跟随助手默认专家”只继承专家值。
实现后若要支持完全退出独立群设置，应另行设计共享上下文范围变化的显式流程。

模型修订应明确补齐当前 Bridge 文档尚未详述的群策略、群连续会话和生效时点。
本方案保持 ADR 0001 中 governance 与交互模式独立的决定；把交互设置从 Bot 扩展到群，
并为旧 Bot 级模式保留兼容路径，不把这种扩展解释成 governance 或部署拓扑变化。

## 7. 验收场景

| 场景 | 预期 |
| --- | --- |
| 同 Bot 的 A 群配置 Reviewer＋单会话，B 群配置 Coder＋话题模式 | 各自使用所选专家；A 群复用一个连续 Session，B 群按话题新建 |
| 两群同时首次触发连续会话；同群多人并发触发 | 群之间 Session 不同，同群只创建一个；Turn 输出准确回源 |
| 同群两个 Bot 分别配置 | 设置、绑定、stream 和回复均不串用 |
| 两个用户在隔离模式中各开一个话题 | 每个话题独立，执行身份来自实际发起者，缺少身份时不降级启动 |
| 用户在别人已有话题继续输入 | 保留原会话身份，后续操作经过 execution authorization |
| 默认专家从 A 改 B | 旧话题与当前连续会话仍为 A，新 Session 为 B |
| 本次显式 `/run` 或 `/bind` | 专家按显式请求/已有 Session 决定，群默认与隔离约束保持 |
| 模式切换、连续会话换代发生在有任务执行时 | 已接受任务正常完成并回原入口，旧连续会话不再接受新任务 |
| 开启隔离后旧普通话题仍存在 | 界面说明已有话题保留原环境，新建入口及绑定校验执行新要求 |
| Profile 不存在、Pack 被移除、模型不兼容或隔离 Runtime 不可用 | 明确报错，无静默改专家、改模型或降低隔离 |
| 重启、重复事件、重复点击保存、旧卡片回调 | 恢复群设置及绑定；输入/保存幂等；过期版本不能覆盖新值 |
| 未授权成员更改配置或伪造其他群的卡片参数 | 后端按 owner、Bot 与群范围拒绝，不仅依赖前端按钮隐藏 |
| Bot 默认 singleton，某群单独配置话题模式并开启值守 | 该群值守正常运行，未配置群保持旧行为 |
| 升级后仅打开状态页 | 不启用群策略、不创建 Session、不重写旧默认 |

实现阶段先更新公共 Bridge/Thread Context 模型，再改存储、路由及行为测试。
涉及命令、配置元数据或 MCP 契约时运行对应文档生成器；冻结最终代码后按仓库要求运行完整门禁。
完整门禁及真实 L4 结果见本次验证报告；环境不支持的能力明确列为未覆盖。

## 9. 本机运维入口

在运行 Hub 的机器上，使用相同安装目录和 Bot profile：

```sh
amux bridge feishu group-settings show <chat-id> --profile default > group.json
# 编辑完整 JSON；保留 bridge_id、chat_id 和 version。
amux bridge feishu group-settings apply <chat-id> --profile default --file group.json
amux bridge feishu group-settings new-conversation <chat-id> --profile default --expected-version <version>
```

CLI 直接使用本机 Bridge 数据库，与远端 Hub 地址配置无关。保存完整配置并进行版本比较；
JSON 缺字段、非法取值或旧版本均被拒绝。目标在线、执行身份和隔离就绪状态在实际启动时检查。
